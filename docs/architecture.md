# U Link 架构说明

## 当前架构决策

第一版 MVP 采用腾讯云自部署路线。

核心原则是先用一个 PayloadCMS 项目同时承载后台管理、内容模型和主要业务 API。这样可以尽快完成学生登录、会员、微信支付、金融内容发布和学校数据管理，避免第一版拆成过多服务。

后续当会员权益、支付、活动报名、咨询线索、实习申请、合作机构等逻辑变复杂时，再从 PayloadCMS 项目中拆出独立业务服务。

## 系统组成

```text
微信小程序
  |
  | HTTPS API
  v
腾讯云自部署应用服务
  |
  |-- PayloadCMS Admin
  |-- Payload Collections
  |-- 微信登录 API
  |-- 会员 API
  |-- 微信支付 API
  |-- 内容 API
  |-- 学校数据 API
  |
  v
PostgreSQL
  |
  v
腾讯云 COS
```

## 小程序端

小程序端负责学生侧体验：

- 微信登录。
- 基础资料完善。
- 会员购买和会员状态展示。
- 金融职业内容浏览。
- 学校相关数据展示。
- 简历、职业测评等第三方服务入口。

第一版优先考虑原生微信小程序，以便贴近微信登录、手机号授权和微信支付流程。

## PayloadCMS 后端

第一版 PayloadCMS 同时承担三类职责：

1. 内容管理后台。
2. 业务数据后台。
3. 小程序 API 服务。

### 内容管理

PayloadCMS 管理：

- 金融职业内容分类。
- 金融职业文章/课程/活动/机构介绍。
- Banner、推荐位和首页模块。
- 第三方服务入口。
- 学校、校区、城市和标签数据。

### 会员与支付

第一版也可以在 PayloadCMS 项目内实现：

- 学生用户集合。
- 会员套餐集合。
- 会员订单集合。
- 微信支付下单接口。
- 微信支付回调接口。
- 支付成功后的会员状态更新。

支付相关接口必须走服务端，不允许小程序直接处理敏感支付密钥。

### 学生登录与指导员认证

第一版学生登录和认证也先放在 PayloadCMS 项目内实现，由 PayloadCMS 提供小程序 API 和后台数据管理。

小程序登录链路：

1. 小程序调用微信登录，服务端换取 openid/unionid。
2. 小程序优先通过微信手机号授权获取手机号。
3. 如果无法授权手机号，则通过短信验证码验证手机号。
4. 小程序提交真实姓名、性别、生日、学院、专业、班级和协议勾选状态。
5. 服务端校验手机号唯一性、学院/专业/班级有效性，创建或更新学生资料。
6. 学生进入“待认证”状态。

账号主身份以微信 openid/unionid 为准；手机号用于学生资料、指导员权限匹配和重复注册判断。同一手机号不允许绑定多个学生账号。手机号修改必须重新验证，并重新检查是否冲突。

指导员权限由班级数据配置产生：班级记录可绑定多个指导员手机号，同一指导员手机号也可绑定多个班级。指导员登录后，服务端使用其当前已验证手机号查询可管理班级，并只返回这些班级下的学生认证数据。

学生状态流转：

```text
未提交资料
  |
  v
待认证
  |-- 指导员确认 --> 已认证
  |-- 指导员标记异常 --> 异常
  |-- 学生重新提交资料 --> 待认证

已认证
  |-- 修改姓名/学院/专业/班级 --> 待认证
  |-- 修改手机号并重新验证 --> 已认证并重新计算权限
```

学生端不直接展示“异常”字样，对应状态显示为“需确认”。

订阅消息只作为提醒增强，不作为流程依赖。指导员和学生都需要在小程序内主动订阅后，后端才发送对应模板消息。服务号通知不进入第一版。

## 数据库

优先使用 PostgreSQL。

生产环境的 PostgreSQL 必须作为独立持久化资源存在，不随 PayloadCMS 应用重新部署而重建。可以使用腾讯云数据库 PostgreSQL，也可以在 CVM/轻量服务器上自建 PostgreSQL，但数据库数据目录必须挂载到独立云硬盘或明确的持久化卷，并配置定期备份。

应用发布、容器重建、Node 进程重启或镜像更新，都不允许清空数据库、重新初始化业务表或覆盖生产数据。数据库迁移必须作为单独步骤执行，并在执行前保留可回滚备份。

初始数据可包括：

- admins：后台管理员。
- students：学生用户。
- schools：学校数据。
- colleges：学院数据。
- majors：专业数据。
- classes：班级数据。
- instructor_assignments：指导员与班级绑定关系，可由 classes 中的指导员手机号配置生成。
- student_verification_logs：学生认证状态变更记录。
- notification-subscriptions：小程序订阅消息授权/可用次数记录。
- membership_plans：会员套餐。
- membership_orders：会员订单。
- memberships：会员状态。
- media：内容封面、文章图片、附件和运营素材。
- finance_categories：金融内容分类。
- finance_contents：金融内容。
- service_links：第三方服务入口。

具体集合命名可在实现 PayloadCMS 时按 Payload 习惯调整。

## 文件存储

图片和附件使用腾讯云 COS，不存放在应用服务器本地磁盘。

生产环境不允许把用户上传图片、内容封面、附件或运营素材存到应用容器本地目录。应用本地目录可以用于临时缓存，但缓存内容必须可以随时删除，不能作为唯一数据来源。

PayloadCMS 使用 `media` 上传集合管理文件。生产环境通过官方 `@payloadcms/storage-s3` 插件连接腾讯云 COS 的 S3 兼容接口；未配置 `COS_BUCKET` 时只能作为本地开发上传，不能用于线上运营。

适合放入 COS 的资源包括：

- 内容封面图。
- 文章图片。
- 学校 logo。
- 合作机构 logo。
- 课程或活动附件。

## 部署

第一版部署在腾讯云，具体形态待确认：

- CVM。
- 轻量应用服务器。
- 容器化服务。

生产环境需要：

- HTTPS 域名。
- Nginx 或等价网关。
- PayloadCMS 应用进程管理。
- 独立持久化 PostgreSQL，不跟随应用重新部署而销毁。
- PostgreSQL 定期备份和上线前手动备份。
- COS 权限配置。
- 微信小程序合法请求域名配置。
- 微信支付回调域名配置。

### 持久化要求

第一版上线前必须确认以下规则：

- 应用服务无状态化：重新部署 PayloadCMS/Next.js 只替换代码和运行环境，不保存唯一业务数据。
- 数据库存储独立：`DATABASE_URL` 指向持久化 PostgreSQL，生产环境不得使用一次性容器内置数据库。
- 文件存储独立：PayloadCMS 上传文件接入腾讯云 COS，不依赖应用服务器本地磁盘。
- 密钥独立管理：`PAYLOAD_SECRET`、数据库密码、微信支付密钥、COS 密钥等通过服务器环境变量或密钥管理配置，不写入仓库。
- 备份先行：涉及数据库结构迁移、批量导入、上线发布前，先做数据库备份。
- 回滚可行：发布包回滚不应影响数据库和 COS 文件；如迁移不可逆，需要先准备数据回滚方案。

本地开发的 `docker-compose.yml` 使用 named volume `ulink_postgres_data` 保存 PostgreSQL 数据。该配置只用于开发环境，删除 volume 会删除本地数据；生产环境需要使用更明确的持久化资源和备份策略。

## 暂不采用的方案

第一版不把微信云开发作为主要业务数据存储。

原因是本项目第一版就需要内容发布、学校数据编辑、会员订单和后续业务逻辑扩展。PayloadCMS 更适合作为内容和运营后台，腾讯云自部署也更适合后续复杂业务逻辑。

微信云开发仍可作为后续辅助能力评估，但不是当前主架构。

第一版不接服务号通知。原因是当前没有服务号，且服务号模板消息需要额外主体、关注关系和 openid/unionid 打通。学生认证提醒先使用小程序订阅消息和小程序内红点/数量提示。

- COS bucket、访问权限和图片处理方案。
- 微信支付商户号、结算主体和回调地址。
- 学院/专业/班级批量导入格式。
- 腾讯云短信服务签名和模板。
