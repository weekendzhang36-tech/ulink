# U Link 开发检查清单

本清单用于每次开始需求、提交代码或准备部署前快速自查。完整原则见根目录 `DEVELOPMENT_PRINCIPLES.md`，日常流程见 `docs/development-workflow.md`。

## 开发前

- 明确这是原型、demo、fixture、本地开发，还是生产路径。
- 写清用户从哪里进入、看到什么、点击什么、创建或更新什么数据，以及下一步由哪个页面或服务负责。
- 确认本次改动涉及哪些业务对象：学生、手机号、认证、会员、订单、支付、内容、预约、服务入口或学校数据。
- 如果涉及持久化记录，确认该记录对应真实用户动作或真实业务事件，而不是为了适配接口形状临时落库。
- 如果涉及第三方服务，确认小程序只展示入口、说明、跳转或咨询承接，不把外部能力伪装成自研完成。

## 实现中

- 后台先在服务层表达业务规则，再由 route handler 适配 HTTP 请求。
- 小程序页面通过统一 API wrapper 调接口，不在页面里散落请求细节。
- 生产路径不能用假数据、默认值、前端 fallback 或空壳文案掩盖接口、数据库、支付、登录、文件上传失败。
- 空状态、加载失败、未配置、未开放要如实展示，并给用户可理解的下一步。
- 跨页面传递稳定引用，例如内容 ID、订单号、预约 ID 或服务入口 ID；进入页面后重新读取页面拥有的数据。
- 支付、会员、认证、预约名额等状态以服务端持久化结果为准，不以前端按钮回调直接判定成功。

## 持久化与密钥

- 生产 PostgreSQL 必须是独立持久化资源，不能跟随应用容器、镜像或部署重建而清空。
- PayloadCMS 上传、内容封面、附件、学校素材和合作方资料必须接 COS 或明确对象存储。
- `PAYLOAD_SECRET`、数据库密码、微信 AppSecret、微信支付密钥、COS 密钥和短信密钥只能来自环境变量或密钥管理。
- 数据迁移、批量导入、支付相关改动和生产发布前，先确认备份和回滚方案。

## 提交前

- 新增或修改业务规则时，先补覆盖本次行为的测试；不要为了旧测试硬改产品代码。
- 涉及后台/API/业务规则时运行：

```bash
pnpm verify:cms
```

- 涉及小程序页面、JSON 配置或 API wrapper 时运行：

```bash
pnpm verify:miniprogram
```

- 提交前完整检查：

```bash
pnpm verify:precommit
```

## 完成标准

- 用户能理解当前状态和下一步，不出现运营侧或实现侧的内部文案。
- 失败、空状态和未开放状态真实可见，不被假内容遮住。
- 业务边界清楚，数据对象的创建、更新、读取和归属没有混用。
- 订单、会员、支付、认证、内容发布、预约和服务入口状态都由后台持久化数据决定。
- 文档已同步更新，下一次继续开发时不用重新追问同一口径。
